# M1 Chrome Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver Issue #16 through child Issues #37 and #38: a routed, safe issue-detail flow plus complete space lifecycle and stale/offline chrome.

**Architecture:** Keep `Control` as the server-snapshot authority and the existing canvas `StarMap` as the renderer. Add a small hash `Route`, thin fetch wrappers, and focused Svelte components; `App` derives active space/issue and owns only composition and documented fallbacks.

**Tech Stack:** Svelte 5 runes, TypeScript 6, Vitest/jsdom, Vite+, `marked`, `dompurify`, existing Rust/Axum server APIs, native Windows PowerShell.

## Global Constraints

- Native Windows 11 only; use PowerShell, `vp`, `cargo.exe`, and Windows paths.
- The approved design source of truth is `D:\dev\stellr\docs\superpowers\specs\2026-08-02-m1-chrome-design.md`; do not recreate it in this worktree.
- All new production behavior follows red-green-refactor; observe the expected failure before implementation.
- All chrome colors come from the existing CSS token block; no raw component colors.
- Keep `Control` authoritative for snapshots and `StarMap` authoritative for canvas rendering.
- Preserve CURRENT/READY focus, black background, star grammar, deterministic layout, and existing token handling.
- Hash routing is canonical `#s=<spaceId>&i=<positiveIssueNumber>`.
- With no routed space, select the first available space; add selects the new space; removing the active space falls forward and clears issue selection.
- Raw issue body HTML is never inserted; Markdown output always passes through DOMPurify.
- Maintain `CHANGELOG.md` as append-only, newest-first, under `Unreleased`.
